# 实验报告：Phase 1 — 场景加载与 RGB 采集模块

**日期**: 2026-05-19

---

## 一、阶段目标

这个阶段要完成整个项目的基础设施——让机器人能在 AI2-THOR 的 3D 室内场景里动起来，同时把视觉数据记录下来。具体来说三件事：

1. 封装 AI2-THOR 控制器，提供一套清晰的操作接口来加载场景、移动机器人、查询状态
2. 定义规范的数据结构，把机器人的位姿、传感器数据、动作结果这些概念理清楚
3. 做一个手动控制程序，能通过键盘操控机器人探索场景，同时自动采集 RGB 图像并导出

---

## 二、整体设计

### 2.1 控制器（ThorController）

控制器是整个系统与 AI2-THOR 仿真器交互的唯一入口。设计上考虑了几个点：

首先是生命周期管理。AI2-THOR 的 Controller 对象创建后会启动一个 Unity 进程，如果忘了关闭就会一直占用资源。我用了 Python 的 context manager 来解决——`with ThorController(...) as ctrl:` 进入时初始化，退出时自动释放，不会遗漏。

其次是动作与观察的分离。每个 `step(action)` 执行一个动作，返回一个 `ActionResult` 对象。这个对象包含四个独立信息：动作是否成功、执行后的 agent 状态、当前的传感器数据（RGB 图像）、以及步数统计。这样做的好处是，调用方一眼就能知道这一步发生了什么，不需要再去读全局状态。

最后是寻路能力。参考 remembr 项目的做法，在控制器里集成了 A* 寻路。场景中有 `GetReachablePositions` 接口可以拿到所有可走的位置，我把这些位置映射成 0.25m 的网格（和 AI2-THOR 的默认步长一致），然后用 A* 在网格上搜索最短路径。控制器提供了 `plan_path()` 做纯计算、`navigate_to()` 做逐步执行，两者分开方便调试。

### 2.2 数据结构

定义了五个核心类型，都在 `src/common/types.py` 里：

- `Vec3`：三维向量，处理 AI2-THOR 里到处出现的 `{"x": ..., "y": ..., "z": ...}` 坐标。带了 `from_dict()` 从 dict 构造和 `distance_to()` 计算两点的 XZ 平面距离——因为在室内导航里我们只关心水平面上的距离。
- `AgentState`：机器人在某一时刻的完整位姿，包括位置、水平朝向、垂直俯仰角、碰撞标记。
- `SensorData`：传感器读数，目前主要有 RGB 图像，深度图作为可选项保留。
- `SceneInfo`：场景元数据，包括场景名、物体列表、agent 初始状态。
- `ActionResult`：执行一个动作后的完整结果，把动作名、成功标记、新 agent 状态、新传感器数据打包在一起。

这些类型之间没有循环依赖，每个类型只做一件事，后面 Phase 2 和 Phase 3 可以直接复用。

### 2.3 RGB 采集（FrameCollector）

`FrameCollector` 的设计目标是"开箱即用"——创建一个 collector 实例，每步调 `record()`，会话结束调 `export_video()`，中间不用管路径管理。

每次运行自动在 `outputs/` 下创建一个时间戳命名的会话目录，结构如下：

```
outputs/20260519_143022_FloorPlan1/
  screenshots/          ← 过程中手动保存的单帧截图
  frames/               ← 导出为 PNG 序列时放这里
  trajectory.mp4        ← 导出为视频时生成这个文件
```

每个 `FrameRecord` 不光存 RGB 图像，还附带步数、动作名、位置、朝向和时间戳，这样导出视频时可以在每帧上叠加这些信息，方便后续分析和调试。

## 三、手动控制程序

`src/cli/manual.py` 是这个阶段的交互入口。启动后进入一个终端命令行循环，用户可以输入指令控制机器人：

| 按键 | 功能 |
|------|------|
| w / s | 前进 / 后退 0.25m |
| a / d | 左转 / 右转 90° |
| q / e | 微调转向 30° |
| r / f | 抬头 / 低头 |
| go \<物体\> | A* 自动导航到指定物体旁边 |
| look \<物体\> | 转向面对指定物体 |
| list | 列出场景所有物体及坐标 |
| where \<物体\> | 查询到该物体的距离 |
| desc | 用 VLM (DeepSeek) 描述当前画面 |
| shot | 保存当前画面截图 |
| video | 导出轨迹视频 |
| frames | 导出帧序列 PNG |
| quit | 退出（自动导出轨迹视频） |

每次操作后终端会打印机器人的新位置、朝向、动作是否成功，以及位置的变化量。如果动作被墙壁挡住，会显示 `BLOCKED (wall/obstacle)`，方便判断要不要转向。

关于界面选择：一开始想用 OpenCV 的 `imshow` 做实时画面显示，但发现在 WSL 环境下因为缺少 X Server 会直接崩溃。权衡之后改成了纯终端模式——位置和朝向信息在终端实时打印，RGB 画面自动保存到 `outputs/` 目录下，用户可以在 Windows 资源管理器里打开截图查看当前视角。虽然少了一点实时沉浸感，但换来的是更好的跨平台兼容性，而且所有帧都有持久化保存，调试的时候很容易回溯任意时刻的状态。

## 四、开发中遇到的问题

### 4.1 碰撞后动作失效

这是调试花时间最长的一个问题。现象是：机器人在墙边按 w 前进撞墙（正常，前方有障碍），然后按 s 想后退，但有时候按一次 s 没用，要按两次才真的往后移动一步。

一开始怀疑是键盘输入的问题，加了日志排除。后来怀疑是 AI2-THOR 的 MoveBack 动作本身不稳定，查了一圈文档和论坛没找到相关讨论。

最终通过逐帧对比 `event.metadata.lastActionSuccess` 和 `agent.isColliding` 找到了根因：AI2-THOR 底层的 Unity 物理引擎在执行 MoveAhead 撞墙后，会在 agent 上施加一个碰撞约束。这个约束不会因为下一个动作是 MoveBack 就自动解除——Unity 认为 agent 还"卡"在墙上，MoveBack 也被物理引擎拦截。等第二个 MoveBack 到来时，上一个（失败的）MoveBack 已经把约束清掉了，所以才能动。

解决方式：在 `step()` 里，当移动动作失败时，立刻执行一个 `Pass`（空操作）。`Pass` 不移动 agent，但会触发 Unity 重新走一遍物理计算流程，从而清掉残留的碰撞状态。这样下一个动作就能正常执行了。

### 4.2 画面与坐标时间戳不一致

测试 w-s-w-s 交替移动时观察到一个很奇怪的现象：终端打印的坐标确实往前了（从 x=-1.25 变成 x=-1.50），但保存下来的截图看起来像是后退了——坐标和画面给人相反的感知。

排查后发现是 AI2-THOR 的事件机制导致的。`controller.step(action)` 返回的 Event 对象里，`cv2img` 是 Unity **执行动作前**渲染的画面，而 `metadata["agent"]["position"]` 是**执行动作后**的坐标。也就是说，同一个 Event 里的图像和位置数据有本质上的时间差。

这个行为在 AI2-THOR 的文档里没有明确说明，是实际调试才发现的。解决的方式是：在每个动作后面无条件跟一个 `Pass`，`Pass` 不移动但会触发 Unity 在新位置重新渲染，然后把 `Pass` 返回的画面作为 `ActionResult` 的传感器数据。这样坐标和图像就始终在同一个时间点上了。

这个修复还顺手解决了 4.1 的问题——每个动作后面都有 `Pass`，碰撞约束总是在下一帧被清除。

### 4.3 部分物体无法被 YOLO 识别

在早期测试时发现了另一个问题：输入 `go to the door`，机器人永远找不到门。原因在于 YOLOv8 的检测能力受限于 COCO 数据集的 80 个类别，"door" 不在这 80 个类别里。所以不管门有没有出现在视野中，YOLO 的检测结果里压根不会出现和 "door" 相关的 label。后续的 CLIP 匹配、距离估计、目标接近决策，全部在第一步就断掉了，机器人只能一直乱走直到达到最大步数。

这个问题触及了纯检测式感知的一个根本局限：不管你用多好的匹配算法（CLIP），如果你的检测池里压根没有合理的目标候选，匹配就无从谈起。在后续的 Phase 2 感知管道设计中，需要从两个方向解决：一是把 CLIP 的匹配范围从"名称过滤后的候选"扩大到"所有检测结果"，利用 CLIP 的跨模态能力在视觉级找最相似的物体；二是加一个与感知无关的距离安全网，通过 AI2-THOR 直接查询机器人与目标的真实距离，当距离小于阈值时直接终止，不依赖感知模块的判断。

## 七、小结

Phase 1 搭好了场景加载和 RGB 采集的基础。控制器、数据结构、采集模块三个组件的职责划分比较清楚，后续 Phase 2（感知）和 Phase 3（决策）可以在这一层之上搭建。

在开发过程中遇到的最有价值的几个问题，本质上都跟 AI2-THOR 的仿真器行为有关——Unity 的物理残留、事件内数据的时间戳差异、检测模型的类别限制——这些问题不是靠"调 API"就能发现的，必须在每一步验证数据的一致性才能定位。这也提醒在后续模块的开发中，不能想当然地依赖仿真器的行为，关键路径上要加断言和合理性检查。

WSL 下的 GUI 可用性是一个可以优化的点。目前手动 demo 通过纯终端 + 截图的方式绕过了这个问题，但如果后续想做人机协作或者实时演示，可以考虑通过 VcXsrv 配置 X Server，或者用更轻量的方式（比如把画面推到一个简单的本地 HTTP 页面）。
