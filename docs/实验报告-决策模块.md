# 实验报告：Phase 3 — 决策模块

**日期**: 2026-05-26

---

## 一、阶段目标

在前两个阶段完成场景控制（Phase 1）和视觉感知（Phase 2）之后，这个阶段要建立从自然语言指令到动作执行的完整决策闭环。具体来说：

1. 设计任务解析器，将用户的自然语言指令转为结构化的任务描述
2. 实现两种决策策略——基于规则的确定性策略（Rule Policy）和基于视觉语言模型的策略（LLM Policy）
3. 决策过程中结合感知管道输出和 AI2-THOR 元数据，感知失败时自动 fallback 到 A* 寻路
4. 提供命令行演示程序，支持单任务执行和交互式多任务测试

## 二、模块设计

### 2.1 数据结构 (`types.py`)

**TaskSpec** — 任务解析器的输出，包含四个字段：

- `task_type`：`"navigation"` 或 `"interaction"`，决定后续行为模式
- `target`：目标物体名称，如 `"chair"`、`"refrigerator"`
- `interact_action`：交互动作类型，`"OPEN"` / `"PICKUP"` / `"TOGGLE"`，导航任务为空
- `raw_text`：保留原始指令文本，供 LLM Policy 使用

**ActionDecision** — 策略每步的决策输出：

- `action`：要执行的动作字符串（`"MOVE_FORWARD"`、`"TURN_LEFT"`、`"STOP"` 等）
- `done`：任务是否完成（True 时决策循环终止）
- `confidence`：策略对本次决策的信心（0-1）
- `reason`：人类可读的决策理由

特殊动作 `"NAVIGATE_TO:<object_name>"` 是策略向决策循环发出的信号，表示"在当前画面中找不到目标，请求用 A* 寻路直接导航到目标坐标"。

### 2.2 任务解析器 (`parser.py`)

`TaskParser.interpret(text)` 采用关键词匹配策略，分三个优先级：

1. **交互动词检测**：先检查是否以 `open`、`pick up`、`turn on` 等交互动词开头。多词短语（如 `turn on`、`switch off`）优先于单词匹配，避免误触发。
2. **导航短语检测**：检查是否包含 `go to`、`find`、`navigate to` 等导航短语，提取短语后面的目标物体名。
3. **默认回退**：无法匹配时，将整句作为导航目标处理。

示例：
```
"Go to the chair"                → navigation, target="chair"
"Open the fridge"                → interaction, target="fridge", action="OPEN"
"Pick up the mug"                → interaction, target="mug", action="PICKUP"
"Turn on the lamp"               → interaction, target="lamp", action="TOGGLE"
"chair"                          → navigation, target="chair"
```

### 2.3 抽象策略接口 (`base.py`)

`DecisionPolicy` 是 ABC，定义统一的 `decide()` 接口：

```python
def decide(self, *, rgb, detections, agent_state, task, step_count) -> ActionDecision
```

策略不持有控制器引用，不直接修改环境状态。所有输入通过参数传入，输出单一 `ActionDecision`。好处是策略可以脱离仿真环境单独测试——给一组 mock 的 detections 和 agent_state 就能验证行为。

`reset()` 方法用于在 episode 之间清空内部状态（如扫描计数器、对话历史）。

### 2.4 Rule Policy (`rule_policy.py`)

基于规则的确定性决策，不依赖任何外部 API。核心算法每步执行：

**步骤 1：目标匹配。** 在 `detections` 中模糊搜索目标：
- 精确匹配（大小写不敏感）：`"chair" == "chair"`
- 别名扩展：通过内置同义词表将 `"fridge"` 映射为 `"refrigerator"`，`"sofa"` 映射为 `"couch"` 等
- 双向子串匹配：`"dining" in "dining table"` 或 `"chair" in "armchair"`

**步骤 2：感知引导接近。** 目标可见时采用两级距离阈值：
- 距离 ≤ 1.0m（STOP）且目标在画面正中：导航任务→STOP，交互任务→执行 INTERACT_* → STOP
- 1.0m < 距离 ≤ 1.5m（NEAR）：若未正对目标则先微调转向，已正对则前进靠近
- 距离 > 1.5m：根据 `screen_position` 决定左转/右转/前进，远处卡住检测（连续前进 >3 次且碰撞→旋转脱困），近处卡住检测（>4 次）
- 这意味着 agent 不会在 1.46m 就直接停住，而是会继续靠近到 1.0m 以内

**步骤 3：搜索与 fallback。** 目标不可见时：
- 原地旋转扫描（左右交替，每次 90°，共 4 次）
- 扫描仍找不到 → 输出 `NAVIGATE_TO:<target>`，决策循环接收到后调用 `ctrl.navigate_to_object()` 执行 A* 导航

**状态管理。** 每个 episode 之间需要 `reset()` 清空内部计数器。扫描计数器、旋转方向、连续前进计数等都封装在 `_RulePolicyState` 中。

### 2.5 LLM Policy (`llm_policy.py`)

用视觉语言模型做决策，每步发送当前画面 + 感知摘要 + 任务描述给 VLM，解析其返回的 JSON 动作。

**System Prompt 设计**：明确定义动作空间（10 个动作）、每个动作的效果（步长 0.25m、旋转 90°/30° 等）、以及任务完成规则。强调"如果目标不可见就旋转搜索"和"卡住时旋转脱困"。

**检测摘要构建**：从 `detections` 中取前 20 个，每条格式化为 ` - label (pos=left/center/right, dist=X.XX m, conf=0.XX, clip=0.XX)`。同时附上当前 heading 和碰撞状态。

**消息格式**：使用 OpenAI Vision API 标准格式——`content` 为数组，包含 `text` 和 `image_url`（base64 JPEG）。保留上一轮对话记录提供时序上下文，避免重复决策。

**响应解析（三级容错）**：
1. 提取 markdown 代码块中的 JSON：`` ```json {...} ``` ``
2. 提取文本中第一个裸 JSON 对象：`{...}`
3. 兜底行为：解析失败时默认 `TURN_LEFT`（安全扫描）
4. 动作验证：不在已知动作空间内的动作被强制替换为 `STOP`

**API 兼容性**：兼容所有 OpenAI Vision API 格式的服务（DeepSeek-v4-pro、GPT-4V、Qwen-VL 等），通过 `OPENAI_API_KEY` 和 `OPENAI_BASE_URL` 环境变量配置。无 API Key 时自动退化为旋转扫描行为，不会崩溃。

### 2.6 决策循环 (`decide.py`)

决策循环是 CLI demo 的核心，负责将策略、感知管道、控制器三者串联：

```
for step in range(max_steps):
    1. ctrl.get_current_view()           → 获取当前帧
    2. pipeline.process(rgb, controller=ctrl) → 感知（距离被 AI2-THOR 真值覆盖）
    3. policy.decide(rgb, detections, ...)    → 决策
    4. if done / STOP → 评估任务完成情况
    5. if NAVIGATE_TO:X → ctrl.navigate_to_object(X)
    6. else → ctrl.step(action)
```

**任务完成评估**：STOP 后检查 `ctrl.distance_to(target)`：
- 导航任务：距离 ≤ 1.5m 视为成功
- 交互任务：信任策略判断（AI2-THOR 交互动作的效果难以从外部验证）

**两种运行模式**：
- 单任务模式：`--task "Go to the chair"`，执行一个 episode 后退出
- 交互模式：不指定 task，提供 `run`/`rule`/`llm`/`info`/`detect`/`list` 等命令

## 三、关键设计决策

### 3.1 感知不完美时的兜底机制

YOLO 微调后 mAP@0.5=0.672，仍有 ~33% 的物体可能检测不到。Phase 3 不要求感知完美——Rule Policy 在 4 次扫描仍未找到目标时，自动降级为 A* 导航（利用 AI2-THOR 的物体坐标元数据）。这个兜底保证了任务不会因为感知失败而卡死。

### 3.2 策略与环境解耦

`DecisionPolicy.decide()` 不接收 `controller` 参数，只接收结构化的观测数据。这意味着：
- 策略可以在没有仿真器的情况下进行单元测试
- Rule Policy 和 LLM Policy 可以无缝切换，共用同一个决策循环
- 未来替换感知模块（比如换掉 YOLO）不影响决策逻辑

### 3.3 同义词映射

用户说"fridge"但 YOLO 检测到"refrigerator"，用户说"sofa"但 YOLO 输出"couch"。Rule Policy 内置了 15 组常用同义词映射。这比依赖 LLM 做语义匹配更快更可靠。

### 3.4 安全边界

两个策略都内置了 `max_steps=200` 的硬上限，防止无限循环。Rule Policy 还有卡住检测（连续前进+碰撞→旋转）。LLM Policy 在无 API Key 时回退到安全行为而不是崩溃。

### 6.1 核心优化

**时序置信度滤波**：12 帧滑动窗口记录每类标签的置信度+距离。当前帧标签不匹配时，检查目标标签在历史窗口中的平均置信度，若 ≥0.4 且附近有距离接近的检测框，覆写其标签为目标名。用时间一致性对抗单帧噪声。

**VLM 多模态集成**：
- 每帧标签纠正：千问 VL 看图校验 YOLO 标签，YOLO vs VLM 置信度仲裁
- VLM 探索恢复：目标丢失时 VLM 直接控制 agent 探索（6 步内），发送 Before/After 双图对比
- 低阈值 YOLO (conf=0.15)：多画框多噪声，依赖 VLM 看图过滤

**交互成功率 80.5%**——时序滤波彻底解决了靠近后的标签混乱，Rule 和 LLM 在交互任务上打平。

**导航瓶颈在感知覆盖率**（YOLO 仅检测到 12% 场景物体），非决策策略问题。

## 七、Phase 4: LLMPolicy 多模态改造 (2026-06-08)

### 7.1 改造动机

Phase 3 的 LLM Policy 从未被真正使用——`decide.py --policy llm` 实际创建的是 `RulePolicy(use_vlm_recovery=True)`，即 Rule 主导决策，VLM 仅在目标丢失时介入恢复。而真正的 `LLMPolicy` 类的 `decide()` 方法只发送文本摘要，没有发送图像，VLM 的多模态能力未被利用。

### 7.2 改造内容

**`llm_policy.py`**:
- `decide()` 消息格式从纯文本改为多模态（image_url + text）
- 新增 `_img_to_b64()` 将 RGB 帧编码为 base64 JPEG
- System prompt 更新为"以图像为主要判断依据"

**`decide.py`**:
- `--policy llm` 现在真正使用 `LLMPolicy`（之前绕过了直接用 Rule+VLM）
- 保留 `hybrid`/`rule+vlm` 命令作为中间选项
- 三种策略可切换：`rule` / `llm` / `hybrid`

**`eval_full.py`**:
- 新增 `--policies` 参数支持三策略对比测试
- 有效策略：`rule`、`rule+vlm`、`llm`

### 7.3 对比实验结果 (2026-06-08)

3 场景 × 8 任务 × 3 策略，seed=42：

| Policy | 总 SR | Nav SR | Interact SR | 步数 | 耗时 |
|--------|-------|--------|-------------|------|------|
| Rule | 47.2% | 29.2% | 83.3% | 20.1 | 3.1s |
| **Rule+VLM** | **51.4%** | 29.2% | **95.8%** | 22.2 | 101s |
| LLM(VLM) 每步 | 38.9% | 18.8% | 79.2% | 49.3 | 150s |

**结论：纯 LLMPolicy（每步发图给 VLM 决策）全面劣于 Rule+VLM 混合模式。**

- Rule 做快速逐帧控制（毫秒级），VLM 做视觉理解（标签纠正、目标恢复）
- 每步发图给 VLM 去做 turn/move 决策既慢又不可靠——该方案已废弃
- `--policy llm` 现在等价于 Rule+VLM（最优方案）
